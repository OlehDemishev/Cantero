## Ошибки — в порядке приоритета

P1 — исправить до эксплуатации с реальными пользователями/деньгами. P2 — исправить следующим этапом. «Воспроизведено» ниже означает локальный вызов сервиса с контролируемыми зависимостями.

### 1. P1: приглашение позволяет выдать себя за существующего пользователя

[invites.service.ts](/Users/olehdemishev/bau_geld/apps/api/src/company/invites.service.ts:83), [invites.controller.ts](/Users/olehdemishev/bau_geld/apps/api/src/company/invites.controller.ts:20), [sessions.controller.ts](/Users/olehdemishev/bau_geld/apps/api/src/auth/sessions.controller.ts:12).

`create()` и `listPending()` возвращают администратору сырой invite token. В `accept()` при существующем email используется найденный User, введённый пароль не сравнивается с его хешем, а 2FA не проверяется. После этого создаётся сессия и подписывается JWT с userId этого человека.

Сценарий: администратор компании B приглашает существующего пользователя A, сам принимает приглашение из ответа API с произвольным паролем и получает его userId. CompanyId токена остаётся B, поэтому это не прямое чтение всех данных A. Но глобальные `/auth/sessions` и `/auth/2fa/setup` опираются на userId: доступны сессии жертвы, их отзыв и перезапись её TOTP-секрета. **Воспроизведена выдача JWT существующего пользователя с включённой 2FA без пароля/кода.**

Исправление: существующий пользователь принимает приглашение только после полноценной аутентификации под совпадающим email; invite token разрешает присоединение к компании, но не вход в чужой аккаунт.

### 2. P1: удаление участника и снижение роли не отзывают доступ

[members.service.ts](/Users/olehdemishev/bau_geld/apps/api/src/company/members.service.ts:25), [jwt-auth.guard.ts](/Users/olehdemishev/bau_geld/apps/api/src/common/guards/jwt-auth.guard.ts:44), [roles.guard.ts](/Users/olehdemishev/bau_geld/apps/api/src/common/guards/roles.guard.ts:24), [auth.module.ts](/Users/olehdemishev/bau_geld/apps/api/src/auth/auth.module.ts:22).

Роль, additionalRoles и companyId берутся из JWT сроком на семь дней. Удаление membership, снижение роли и удаление custom role не отзывают сессии. Guard проверяет только состояние сессии и её inactivity timeout, не актуальное членство. Удалённый администратор может продолжать обращаться к API со старой ролью до истечения JWT/отзыва сессии. **Путь guard без запроса membership подтверждён локальным вызовом.**

Исправление: централизованная проверка актуального membership/permissions или версия авторизации, меняемая при отзыве прав. Обновление прав и отзыв должны быть атомарны.

Глобальный поиск restrictedToMembers/projectMember показал, что enforcement сосредоточен только в ProjectsService.

Исправление: единая project-access policy для каждой операции над проектом и его дочерними объектами, включая списки, скачивания, отчёты и экспорт.

### 5. P1: офлайн-данные и операции смешиваются между аккаунтами

[offline-db.ts](/Users/olehdemishev/bau_geld/apps/web/lib/offline-db.ts:3), [offline-queue.ts](/Users/olehdemishev/bau_geld/apps/web/lib/offline-queue.ts:33), [offline-cache.ts](/Users/olehdemishev/bau_geld/apps/web/lib/offline-cache.ts:19), [api-client.ts](/Users/olehdemishev/bau_geld/apps/web/lib/api-client.ts:24), [sw.js](/Users/olehdemishev/bau_geld/apps/web/public/sw.js:84).

## Архитектура

**Основа разумная:** модульный монолит NestJS, отдельный Next.js UI, shared Zod-контракты, Prisma/PostgreSQL и BullMQ. Есть полезное отделение чистых расчётных функций от сервисов, тесты на расчёты/tenant scoping, guards, уникальные ограничения. StockService уже использует serializable transactions с retry — удачный пример для других критичных модулей. Переход на микросервисы не следует из обнаруженных проблем.

**Главный недостаток — инварианты разбросаны по endpoints.** Membership, закрытые проекты, скрытие себестоимости и внешние платежи защищаются локальными проверками. Соседний endpoint легко обходит правило. Нужны единый ActorContext (user/company/current permissions), обязательные policy checks и response projections для ограниченных данных. Доступные Prisma models не должны автоматически становиться форматом публичного ответа.

**Транзакции не совпадают с бизнес-операциями.** Транзакционные примитивы используются лишь в 17 из 171 service-файла; это само по себе не ошибка, но конкретные разрывы в платежах, начислениях и recurring generation уже приводят к дефектам. Следует описать инварианты каждой денежной операции, обеспечивать их unique/check constraints и транзакциями, а побочные эффекты запускать через transactional outbox. Критичный audit trail сейчас fire-and-forget с подавлением ошибки, поэтому может отсутствовать при успешной операции.

**Tenant isolation существует только в приложении.** PrismaService — обычный PrismaClient без tenant context. `prisma/rls.sql` явно не подключён к request lifecycle и находится отдельно от миграций; считать его действующей защитой нельзя. Предпочтительны tenant-scoped access layer и составные FK для связей внутри компании. RLS возможен как дополнительный слой после проработки connection pooling, background jobs и привилегированных операций, а не простого запуска SQL-файла.

**Нет единой модели денег.** В БД Decimal, но сервисы часто преобразуют суммы в Number. Уже подтверждены неверная валюта Checkout и EUR default регулярных счетов. Нужна явная модель amount+currency, единая политика округления, сохранение валюты операции и отдельные переходы состояния платежа/счёта. Не стоит исправлять финансовую целостность только форматированием UI.

**Доставка интеграций ненадёжна.** WebhooksService отправляет сразу из процесса; delivery log хранит результат, но не организует durable retry. Падение процесса теряет события. AuditService также подавляет ошибки. BullMQ уже есть, поэтому outbox → queue → идемпотентный worker можно внедрить без смены стека. На критичных событиях нужны retries/backoff и наблюдаемость.

**Расширение числа экземпляров требует подготовки.** RateLimiterService хранит counters в памяти процесса; StorageService без S3 использует локальный диск; API и queue processors собираются в одном AppModule. Для нескольких replicas нужны shared rate limits, обязательная проверка production config и при необходимости отдельный worker entrypoint. По умолчанию предупреждения о конфигурации не предотвращают небезопасный production startup.

**UI слишком укрупнён и почти не проверяется поведением.** Settings — 2128 строк, estimate detail — 1360, warehouses — 1240, field — 1055. В web нет собственных test/spec-файлов и test script. API вызовы, локальный state, permissions и offline replay распределены по компонентам. Нужны feature hooks, единые query/mutation contracts и браузерные проверки критичных путей. Это можно делать постепенно, без переписывания всех страниц.

**Запросы плохо ограничены для роста объёма.** В сервисах 504 findMany-вызова, многие списки без pagination. ExpensesService дополнительно читает всю историю и для каждой строки заново фильтрует категорию: в худшем случае квадратичная работа. Exports собирают массивы и ZIP целиком в памяти. Приоритет — измерить тяжёлые endpoints, ввести pagination/DB aggregation и фоновые потоковые exports.

**CI проверяет преимущественно isolated correctness.** Нет настоящей БД для migrations/constraints/concurrency, нет browser E2E; lint всё ещё non-blocking, хотя сейчас уже нет ошибок. Добавить чистое применение всех миграций и schema drift check, HTTP integration tests с реальной БД, несколько критичных E2E, стандартную production build. Сначала нужны тесты именно найденных сценариев, а не увеличение количества моков ради покрытия.
