## 2. Безопасность

### Высокая

**S1. OAuth-коллбэки принимают любой JWT компании как `state`** ✅
`apps/api/src/common/oauth/oauth.ts:49` — `verifyState` делает только `jwt.verify` общим `JWT_SECRET`;
access-токен (`auth.service.ts:127`, содержит `companyId`) проходит эту проверку. Коллбэки публичные:
`docusign.controller.ts:37`, `intacct.controller.ts:66`, `autodesk.controller.ts:94`.
Атака: работник без `settings.integrations` подставляет свой bearer-токен в `state` authorize-URL и логинится
в свой DocuSign → коллбэк перезаписывает подключение компании. Дальше контракты идут через аккаунт атакующего;
для Intacct — синхронизация главной книги. Плюс CSRF: `state` не привязан к браузеру.
Решение: `signState` подписывает `{kind: "oauth_state", provider, userId, nonce}`, `verifyState` требует все
поля; nonce — в httpOnly cookie или БД, одноразовый. Accounting и MS Project уже требуют доп. claims — привести
к той же схеме.

**S2. Секретные токены внешних сторон в ответах для сотрудников** ✅
`GLOBAL_OMIT` (`common/prisma/prisma.service.ts:8`) скрывает только `worker.clockInPinHash`.
`contracts.service.ts:28-44` (list/get через `include` без `select` → весь ряд с `clientAccessToken`),
`estimates.service.ts:56-61`, `change-orders.service.ts:51-57`, `signature-requests.service.ts:24-30,166-174`.
Атака: сметчик/бухгалтер с правом просмотра берёт токен из ответа и вызывает
`POST /public/contracts/:token/sign` / `/public/estimates/:token/decision` / `/public/signatures/:token/sign` —
подпись клиента подделана. Дополнительно `signature-requests list()` без `visibleWhere` → видны запросы
закрытых проектов.
Решение: добавить токен-колонки в `GLOBAL_OMIT`, ссылку для клиента отдавать отдельным эндпоинтом
«скопировать ссылку» с правом `*.manage`; `visibleWhere` в list.

**S3. Любой API-ключ имеет полный доступ к SCIM** ✅
`scim/scim.controller.ts:11-13` без `@RequireScope`; `common/guards/api-key.guard.ts:32` проверяет scope,
только если он объявлен. Ключ для BI-чтения может создавать пользователей (сверх оплаченных мест),
привязывать существующего пользователя другой компании (`scim.service.ts:55-68`), выгрузить все email,
разлогинить пользователя во всех компаниях (`scim.service.ts:96-99`).
Решение: scope `scim`, пустой список scope ≠ SCIM; `assertSeatAvailable`; не присоединять существующих
пользователей без согласия; отзывать сессии только текущей компании.

### Средняя

**S4. `ProjectAccessGuard` проверяет только первый найденный `projectId`** ✅
`common/guards/project-access.guard.ts:44-48`: params → query → body. `POST /api/tasks?projectId=<разрешённый>`
с телом `{projectId: <закрытый>}` — гард проверяет разрешённый, `tasks.service.ts:45` пишет в закрытый.
Решение: собрать id из всех источников, проверить каждый (или 400 при расхождении).

**S5. SSO кладёт 7-дневный access-токен в URL и принимает любой токен** ✅
`apps/api/src/sso/sso.controller.ts:67` → `/sso/callback?token=…`; `apps/web/app/sso/callback/page.tsx:20`
сохраняет токен без проверки, что вход начинал этот браузер.
Атака: ссылка с токеном атакующего → жертва незаметно работает в чужой компании (login CSRF). Токен остаётся
в истории, в Cache Storage service worker (`public/sw.js:51-57` кэширует навигации по полному URL) и в Sentry.
Решение: одноразовый код (60 с) + обмен через POST с nonce из `sessionStorage`; `history.replaceState` сразу;
SW не кэширует URL с query и `/sso/`, `/reset-password`, `*/verify`.

**S6. Выход не завершает сессию на сервере** ✅
`apps/web/components/authenticated-shell.tsx:356` — только `clearToken()`; logout-эндпоинта в API нет.
Порталы — то же (`app/portal/page.tsx:229`, `supplier-portal/page.tsx:62`, `subcontractor-portal/page.tsx:129`),
их токены живут 30 дней без отзыва. Токены в `localStorage`, CSP с `script-src 'unsafe-inline'`.
Решение: `POST /auth/logout` (отзыв `sid`), `sid` и отзыв для портальных токенов, короче TTL; дальше —
httpOnly-cookie или короткий access + refresh.

**S7. Киоск: PIN проверяется только в браузере** ✅
`app/field/kiosk/page.tsx:74-101` — после `verify-clock-in-pin` ставится локальный флаг, `POST /time-entries`
уходит с любым `workerId`; `self-scope.service.ts:44` пропускает пользователя с правом на время бригады.
На планшете под учёткой менеджера можно отметить часы за любого и открыть весь `/dashboard`.
Решение: проверка PIN возвращает короткий токен на конкретного работника, эндпоинт киоска его требует;
киоск логинится отдельной device-учёткой с доступом только к киоск-эндпоинтам.

**S8. Плановые и пользовательские отчёты игнорируют закрытые проекты**
`scheduled-reports.service.ts:110-143`, `reports/custom-reports.service.ts:81-95` вызывают выборки без зрителя.
Бухгалтер без доступа к проекту ставит отчёт на любой email → маржа всех проектов.
Решение: хранить создателя отчёта и выполнять от его имени.

**S9. `GET /company` отдаёт всю строку компании любому участнику**
`company.controller.ts:35-38`, `company.service.ts:33-41`: `calendarFeedToken`, Slack/Teams webhook URL,
`franchiseLinkCode`, IBAN, SSO-сертификат. Через ICS-фид видны задачи закрытых проектов; можно постить в Slack.
Решение: явный `select`, секретные поля только с `settings.company`.

**S10. SSO-домен можно занять без подтверждения владения**
`sso.service.ts:38-52, 69-84, 108-130`. Компания-атакующий заявляет `victim.com` → пользователи
`@victim.com` уходят на её IdP и авто-создаются в её компании.
Решение: DNS TXT-верификация (как уже сделано для кастомного домена портала).

**S11. Пробелы в SSRF-блоклисте исходящих вебхуков**
`common/webhooks/webhook-url.ts:6-15` не блокирует `::ffff:169.254.169.254`, `::`, `0.0.0.0/8`,
`100.64.0.0/10`, `fec0::/10`, `64:ff9b::/96`. Решение: нормализовать mapped-адреса, `ipaddr.js`
`range() !== "unicast"` → отказ.

### Низкая
- CSV formula injection: `common/csv.ts:1-6` не экранирует `= + - @` (имена лидов приходят из публичной формы).
- Backup-коды 2FA из `Math.random` (`two-factor.service.ts:21-23`) → `crypto.randomInt`.
- IP-allowlist не действует на API-ключи (`/v1`, SCIM — `@Public`, `ip-allowlist.guard.ts:35-40`).
- Нет rate limit на запрос magic-link в порталах (`portal-auth.service.ts:26-48`), лимитер в памяти процесса.
- Перечисление аккаунтов: signup сообщает, что email занят (`auth.service.ts:30`); login пропускает bcrypt
  для неизвестных email (`auth.service.ts:85-90`); reset-токен проверяется и гасится в два шага — гонка
  (`password-reset.service.ts:63-86`).
- После выхода на общем планшете остаются IndexedDB-кэш и `/api/` в Cache Storage (`lib/api-client.ts:5-7`,
  `public/sw.js:84-91`).
- Файловые ответы API без `nosniff`/`attachment` в части контроллеров (`leads.controller.ts:41,48`,
  `drawing-sheets.controller.ts:93`, `company.controller.ts:71`, `takeoffs.controller.ts:41`); сейчас
  смягчено allowlist'ом MIME. Добавить helmet, проверять magic bytes.
- Sentry без `beforeBreadcrumb`/`beforeSend` (`lib/init-sentry.ts`) — токены из путей `/sign/…`, `/survey/…`
  попадают в breadcrumbs.
- Требует проверки: `environmentUrl` в MS Project не валидируется (`ms-project.controller.ts:11-13`);
  `wageClassificationId` работника не проверяется на компанию (`workers.service.ts:74`).

### Проверено, в порядке
Глобальные гарды (JWT → IP → подписка → проект → роли) и три спеки на покрытие декораторов; изоляция по
`companyId` в выборках; нет `dangerouslySetInnerHTML`/`innerHTML`, нет открытых редиректов; CSP с
`frame-ancestors 'none'`, HSTS, Referrer-Policy; Stripe/Twilio-вебхуки с проверкой подписи; bcrypt 12;

`NEXT_PUBLIC_*` без секретов; next 16.3.5 / react 19.2.8 / pdfjs 6.2.108 — без известных CVE.
